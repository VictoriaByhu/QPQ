# Лаб. 06 — порівняння HTTP і gRPC, ефект кешу

## Як міряли

- Запит: `GET http://localhost:5000/api/aggregator/swaps/2/full` з `X-User-Id` учасника обміну (U2). Обмін містить 2 сесії та розмову з повідомленнями.
- Інструмент: `curl -w "%{time_total}"`, послідовні запити, усі відповіді 200 і порожні `warnings`.
- Кожна серія: новий запуск AppHost (`--launch-profile https`), перший запит — холодний, далі 20 прогрітих.
- Середовище: одна машина, Debug-збірка, контейнери SQL Server, MongoDB і Redis у Docker Desktop.

Щоб порівняти транспорт, а не кеш, для серії gRPC кеш у Swaps і Aggregator тимчасово вимикався локальною зміною, яка не потрапила в репозиторій.

## HTTP (Лаб. 05) проти gRPC (Лаб. 06), без кешу

| Показник | HTTP (Лаб. 05) | gRPC (Лаб. 06) |
|---|---:|---:|
| Холодний запит | 1571,0 мс | 1562,5 мс |
| Кількість прогрітих запитів | 20 | 20 |
| Середнє | 41,0 мс | 41,5 мс |
| Медіана | 35,5 мс | 36,1 мс |
| Мінімум | 27,0 мс | 27,3 мс |
| Максимум | 123,2 мс | 116,6 мс |

**Висновок.** На цьому навантаженні вимірюваного виграшу за часом відповіді gRPC не дав: різниця медіан 0,6 мс менша за розкид між окремими запитами. Вимірювання послідовне, на localhost, з невеликими відповідями, тому мережа й серіалізація, ймовірно, становлять малу частку часу порівняно з роботою БД і проходженням через Gateway. Окремо час цих етапів не вимірювався.

Холодний запит сильно шумить: той самий код у різних запусках давав від 1,6 до 2,4 с, тож одиничне значення не придатне для порівняння.

Перехід на gRPC дав інші зміни, які не видно в часі відповіді:

- типізований контракт у `.proto` замість JSON без схеми;
- один виклик `GetSwapConversation` замість послідовного перебору сторінок `/api/conversations` і `/api/conversations/{id}/messages`;
- явні статуси `NotFound`, `InvalidArgument`, `PermissionDenied`, `Unauthenticated`.

## Ефект кешу (gRPC, кеш увімкнений)

| Запит | Перший | Повторні | Середнє повторних | Медіана повторних |
|---|---:|---:|---:|---:|
| `GET /api/aggregator/swaps/2/full` | 2306,0 мс (холодний) | 20 | 8,7 мс | 7,8 мс |
| `GET /api/skills` | 53,5 мс | 10 | 8,3 мс | 7,4 мс |
| `GET /api/swaps/3` | 42,6 мс | 10 | 8,1 мс | 7,0 мс |
| `GET /api/skills/2` | 31,6 мс | 10 | 7,3 мс | 6,7 мс |

Повторний запит агрегованої картки обслуговується з Redis Aggregator: медіана 7,8 мс проти 36,1 мс без кешу, приблизно в 4,6 раза швидше. Запити до `swaps-api` на повторі читаються з L1 і не виконують SQL. Перші запити цих рядків виконувались уже після прогріву сервісу, тому вони не є холодним стартом.

## Поведінка при збоях

| Сценарій | Результат |
|---|---|
| Redis зупинено, перший запит після зупинки | 200, близько 5–6 с (очікування тайм-ауту клієнта Redis), Warning у лог |
| Redis зупинено, наступні 30 с | 200, без затримки: L2 пропускається |
| `sessions-api` зупинено | 200 за 10 с, `warnings: ["sessions-api is unavailable"]`, відповідь не кешується |
