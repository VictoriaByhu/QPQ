# Контексти піддомену Skills

Піддомен Skills (власник `SkillId`) складається з трьох незалежних контекстів. Кожен має власний API та власну базу. Між базами немає спільних таблиць, JOIN і FOREIGN KEY: контексти обмінюються лише ідентифікаторами та подіями. Кожна сутність належить рівно одному контексту, локальні копії чужих даних позначені нижче.

## Огляд

| Контекст | Відповідальність | Сховище | База |
|---|---|---|---|
| UserSkills (Проєкт №1) | які навички людина пропонує (Offer) і які хоче вивчити (Want): рівень, мови, доступність, статус запису | SQL Server, ADO.NET + Dapper | `QPQ_UserSkills` |
| Catalog (Проєкт №2) | довідник навичок і категорій, теги, назви рівнів | SQL Server, EF Core | `QPQ_Catalog` |
| Matching (Проєкт №3) | підбір пар: хто пропонує те, що потрібно іншому, і навпаки | MongoDB | `QPQ_Matching` |

## UserSkills

| Питання | Відповідь |
|---|---|
| Власні сутності | UserSkill, UserSkillDetail, AvailabilitySlot, UserSkillLanguage, UserSkillStatusHistory, Language (довідник) |
| Агрегат | UserSkill (корінь) разом із деталями, мовами, вікнами доступності та історією статусів; змінюються лише через нього |
| Копії чужих даних | `Skills` (`Id`, `Name`) з Catalog |
| Посилання на користувачів | `UserId`, `CreatedBy`, `UpdatedBy`, `ChangedByUserId` (лише `UserId` з Identity) |
| Подія, яку видає | `UserSkillsChanged` |
| Подія, яку обробляє | `SkillChanged` (оновлення копії навичок), `UserRegistered`, `UserDeleted` |
| Чому такий вибір сховища | запис має життєвий цикл (Active, Paused, Archived) з контрольованими переходами, транзакційна зміна статусу, збережувані процедури й оптимістична конкурентність |

## Catalog

| Питання | Відповідь |
|---|---|
| Власні сутності | Category, Skill, SkillDetail, SkillLevel, Tag, SkillTag |
| Агрегат | Skill (корінь) разом з деталями, рівнями й тегами; категорія та тег існують окремо |
| Копії чужих даних | немає |
| Посилання на користувачів | немає (довідник редагують адміністратори поза доменними даними) |
| Подія, яку видає | `SkillChanged` |
| Подія, яку обробляє | немає |
| Чому такий вибір сховища | розвинена реляційна модель (1:1, 1:N, M:N з власним полем), довідкові seed-дані; запити й міграції зручно вести через EF Core |

## Matching

| Питання | Відповідь |
|---|---|
| Власні сутності | `matches`, `skillStats` (похідна колекція) |
| Копії чужих даних | `userSkillIndex`: копія записів UserSkills (`userSkillId`, `userId`, `skillId`, `type`, `level`, `status`, `languages`, `availability`, `experienceYears`); `skillName` з Catalog |
| Посилання на користувачів | `userId`, `userIds`, `offer.fromUserId`, `offer.toUserId` |
| Подія, яку видає | немає |
| Подія, яку обробляє | `UserSkillsChanged` (оновлює `userSkillIndex`, перераховує пари й `skillStats`), `SkillChanged` (оновлює `skillName`), `UserDeleted` (видаляє документи користувача) |
| Чому такий вибір сховища | це read-модель: документи з вбудованими масивами мов і доступності читаються разом, пари мають різну форму (`oneWay`, `mutual`), записи тимчасові (TTL) |

## Правила доступу

- Права перевіряються за токеном: змінювати навичку, її статус і видаляти її може лише власник запису.
- Персональні дані (ім'я, email, аватар) живуть тільки в Identity, у доменних базах зберігається лише `UserId`.
- Matching віддає користувачеві лише пари, у яких він учасник (`userIds`).
